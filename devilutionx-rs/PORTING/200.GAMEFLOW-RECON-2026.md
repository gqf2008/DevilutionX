# 200. Game-Flow Recon 2026 — 游戏流程层深度侦察

> 侦察日期：2026-07-07
> 范围：启动 → 主菜单 → 角色选择 → 进入游戏（城镇 Tristram）
> 方法：只读源码 + 写本文档。不评估被其他 agent 占用的 `src/levels/`、`src/utils/`、`src/game/player*.rs` 内部，但评估它们**是否被接线进主流程**。
> 取代：`PORTING/151.M80-HONEST-STATUS.md`（2025-12 评估）的流程层结论。

---

## 1. 执行摘要

**核心结论：游戏流程层比 2025-12 评估成熟得多，"启动→主菜单→选角色→进游戏循环"的骨架已完整接线并可运行，但游戏循环进入后只画一个绿色方块——关卡（地图/瓦片/精灵）渲染整条管线从未被调用，这是距离"可玩 Demo"最大的单一缺口。**

具体而言：

- `main.rs`（~2000 行）实现了**完整的 C++ `DiabloMain` 启动序列**：MPQ 加载、选项、窗口、Splash、主菜单循环、选角色、`start_game` → `run_game_loop`，且各环节命名与 C++ 一一对应。
- **主菜单能真实渲染**：从 `spawn.mpq` 加载 PCX 背景图、LOGO、焦点环动画、系统字体文本，鼠标/键盘可选 Single/Multi/Settings/Credits/Exit。这是真实的、资产驱动的 UI，不是存根。
- **选角色能工作**：Warrior/Rogue/Sorcerer + Back，PCX 背景 + 焦点环。
- **MPQ 加载真实可用**：`engine::mpq::AssetManager`（main.rs 实际使用的）能解压 spawn.mpq 的真实文件；新增的 `engine::archive::ArchiveManager` 更完善但**未被 main.rs 使用**（接线机会 #1）。
- **进入游戏循环后，`draw_and_blit()` 只画 `game_state.player.position` 处一个 32×32 绿色方块**。`redraw_viewport()` 是空函数。所有真实渲染能力（CEL/CLX 解码、`dun_render`、`isometric`、`engine::dungeon::TileDecoder`、`levels/town.rs`）**存在但从未被游戏循环调用**。

**离最近可玩里程碑（启动→菜单→新建角色→进入城镇→看到 Tristram 地图和玩家→能走动）的距离**：在理想情况下约 **3-5 个中等工程任务**——核心是"接线"而非"从零实现"。最短路径是让 `run_game_loop` 里的 `redraw_viewport`/`draw_and_blit` 实际调用已有的等距瓦片渲染器，并把 `levels/town.rs` 的 `create_town()` 接到关卡初始化。最大未知是 CLX→SDL 纹理这条桥是否真的通（见第 6 节）。

### 3.2 关键缺口在 `RunGameLoop` → `StartGame(uMsg)` → `LoadGameLevel`

C++ 进入游戏循环后，关卡数据是这样加载的（`Source/diablo.cpp`）：

```
RunGameLoop(uMsg)
├─ StartGame(uMsg)                         ← diablo.cpp:178
│   └─ ShowProgress(uMsg)
│       └─ LoadGameLevel()                 ← diablo.cpp:~3070+
│           ├─ (Town 分支) LoadGameLevelTown
│           │   └─ CreateLevel(ENTRY_MAIN)  ← 实际读 towndata，填 dPiece
│           └─ (地下城) CreateLevel + DRLG
├─ PrepareForFadeIn / PaletteFadeIn
└─ while(gbRunGame):
    ├─ RedrawViewport()    ← 真实渲染 dPiece 到 backbuffer
    └─ DrawAndBlit()       ← 叠 panel/cursor，flip
```

**Rust 现状**：`run_game_loop` 的 `start_game(mode)` 只 `println!`（`game_loop.rs:287`），**完全没有 ShowProgress/LoadGameLevel/CreateLevel 的等价物**。`redraw_viewport`/`draw_and_blit` 是空的/画绿块。这一整段（C++ 约 200 行 + LoadGameLevel 系列 ~250 行）在 Rust 端是**最大空白**。

## 4. 最小可玩 Demo 步骤分解

目标里程碑：**启动 → 主菜单 → 新建角色 → 进入 Tristram → 看到 town 地图瓦片和玩家精灵 → 能用方向键走动（精灵随地图滚动）**。不含战斗/怪物/NPC/物品/UI 面板。

> 约束提醒：本任务不改 `src/levels/`、`src/utils/`、`src/game/player*.rs`（其他 agent 在改）。下列步骤按此边界设计——优先用 `main.rs`/`game_loop.rs`/`game_state.rs`/`engine` 内接线，或新增小型渲染桥。

### Step 1：让 `run_game_loop` 加载 Town 数据（接线 + 小改）
- **做什么**：在 `start_game()`（`game_loop.rs:287`）里，把当前"println 占位"替换为真正加载 Tristram。最小可行方案：用 `engine::dungeon::DungeonLevelData::load_from_mpq()`（能读真 MIN/SOL/TIL）或 `levels::town::create_town()` 填充一个可渲染的瓦片网格。
- **改哪些文件**：`src/game/game_loop.rs`（start_game）；可能需要在 `GameState`（`src/game/game_state.rs`）加一个 `level_data: Option<DungeonLevelData>` 或类似字段。
- **依赖**：`spawn.mpq` 已存在且 `levels\towndata\town.*` 可读（main.rs:767 已验证 `has_file("levels/towndata/town.min")` 可达）。
- **难点**：若用 `levels/town.rs`，需先把它加进 `main.rs` 的 mod 树（见风险 R1）。若用 `engine/dungeon.rs` 则无此问题但需自行拼出 town 的 dPiece 网格（town 是固定布局，可硬编码）。
- **预估**：中等（1-2 天）。主要是数据格式对接。

### Step 2：搭 CLX/CEL → SDL Texture 的渲染桥（新增小模块）
- **做什么**：这是目前**全项目缺失的一座桥**——`CelDecoder`/`load_clx` 产出 `ClxSprite`（调色板化像素），但没有任何代码把它变成 SDL2 `Texture`。需要写一个函数：`fn clx_to_texture(creator, sprite, palette) -> Texture`，把 CLX 像素用调色板展开成 RGBA 再 `create_texture_streaming`。main.rs 里的 `load_pcx_image`→`UiArtImage::to_texture` 已经为 PCX 做了完全等价的事，可作模板。
- **改哪些文件**：新增 `src/engine/sprite_render.rs`（或在 `engine::clx` 里加 `to_rgba(&palette)`），并在 `engine/mod.rs` 导出。
- **依赖**：`engine::palette::Palette`、`engine::clx::ClxSprite`。
- **难点**：CLX 的 RLE 解码正确性 + 调色板索引 0 透明处理。`CelDecoder` 已有单测，可信赖。
- **预估**：中等（1-2 天）。这是把"看起来实现的能力"变成"真能画"的关键。

### Step 3：在 `draw_and_blit` 里用 isometric 渲染器画 town 瓦片
- **做什么**：把 `game_loop.rs` 的 `draw_and_blit`（当前画绿块）替换为：遍历 viewport 内的 dPiece，用 Step 1 的瓦片数据 + Step 2 的纹理桥，按等距投影绘制。最短路径：直接用 `engine::isometric::IsometricRenderer`（已有 `draw_floor_tile`/`draw_checkered_floor`，通过 `window.draw_pixel`，慢但能验证）。
- **改哪些文件**：`src/game/game_loop.rs`（redraw_viewport + draw_and_blit）。
- **依赖**：Step 1（数据）+ Step 2（纹理）。
- **难点**：等距坐标→屏幕坐标的相机/视口计算；`scrollrt.rs` 里有 `ViewportGeometry`/`calc_viewport_geometry` 可复用。
- **预估**：中偏大（2-3 天）。先求"能看到瓦片"，不求性能。

### Step 4：玩家精灵 + 输入移动 + 相机跟随
- **做什么**：把绿块玩家换成真实 CEL 精灵（`plrgfx\walk\*.cel`，spawn.mpq 有）。接 `InputSystem` 的方向输入到 `game_state.player.position`（player_movement.rs 已有逻辑），相机跟随玩家。
- **改哪些文件**：`src/game/game_loop.rs`（事件处理→移动→相机）。
- **依赖**：Step 2（精灵纹理）+ Step 3（视口）。
- **难点**：精灵朝向/动画帧；玩家坐标是 world tile 还是像素需对齐 C++。
- **预估**：中等（1-2 天）。

### Step 5（可选打磨）：淡入/调色板/cursor
- 接 `palette_fade_in/out` 占位（`game_loop.rs:301`）真实生效；用主菜单已加载的 cursor 资产画鼠标。

**总预估**：到 Step 4（"能走动的 Tristram"）约 **6-9 个工作日**，前提是 Step 2 的纹理桥能顺利打通（最大未知）。

## 6. 风险与未知

- **R1（最大未知）："CLX/CEL → SDL Texture" 这座桥从未被验证过。** `CelDecoder` 有单测但只测编码输出，没人把它喂给 SDL 显示过一个像素。Step 2 若卡住（RLE 解码 + 调色板 + 透明索引 + SDL pitch），整个 Demo 路径都会受阻。**建议第一件事就做一个最小 spike：从 spawn.mpq 读一个 CEL，解码，画到屏幕**，验证桥通不通，再铺开。
- **R2：`src/levels/` 不在二进制 mod 树。** 它只在 `lib.rs` 声明，`main.rs` 没有 `mod levels`。意味着 `create_town`/`Dungeon`/`drlg_l1..l4` 这些忠实端口**当前根本没编译进可执行文件**。要用它们必须先解决 mod 结构（但该目录被其他 agent 占用，需协调）。
- **R3：两套并行的地牢系统会让人困惑。** `game/dungeon.rs::DungeonMap`（过程化随机，GameState 在用）vs `levels/gendung.rs::Dungeon`（C++ 忠实，dPiece 层，未编译）。最小 Demo 若用前者，得到的是"随机地牢"不是 Tristram；要用后者需先打通 R2。
- **R4：`dun_render` 输出调色板化 `Surface`（u8），不是 RGBA。** SDL2 的 `Texture` 通常要 RGBA。若走 dun_render 高性能路径，需额外做 `Surface→Texture` 的调色板查表转换（每帧或缓存）。这比 isometric 逐像素更复杂，故最小 Demo 建议先用 isometric（慢但简单）验证，再考虑换 dun_render。
- **R5：`start_game`（game_loop 内）与 `start_game`（main.rs）语义不同。** main.rs 的 `start_game` 建了 `GameState::new(player, false, seed)`——注意 `is_town=false`，且 `DungeonMap::generate(Cathedral)` 生成的是随机 Cathedral 不是 town。要进 Tristram 需改 `is_town=true` 并接 town 数据。
- **R6：音频/电影是纯 stub。** `MoviePlayer::play` 只 println，`AudioManager` init 成功但不播放。对"可玩 Demo"非阻塞，但 Splash 的 logo.smk 不播。
- **R7：selhero 流程简化。** 无角色名输入、无存档列表、无 pfile 持久化、无难度选择。对最小 Demo 可接受（默认 Warrior 进 town），但与 C++ `UiSelHeroSingDialog` 差距大。
- **R8（惊喜）：主菜单/选角色的资产驱动渲染已远超 2025-12 评估。** PCX 背景、LOGO、8 帧焦点环动画、系统字体文本——这些是真实的、可看的 UI，不是占位框。151 文档说"UI 基本为 0%"已过时，实际 UI 流程层约 **70% 完成**。
- **R9（惊喜）：MPQ 管线比评估更成熟。** 不仅 `mpq.rs::AssetManager` 真能解 spawn.mpq，新增的 `archive.rs::ArchiveManager` 还通过了真 spawn.mpq 的端到端集成测试（`two_archives_precedence_overrides` 解出 `levels\l1data\l1.min`）。资源加载层是**最不缺**的一环。

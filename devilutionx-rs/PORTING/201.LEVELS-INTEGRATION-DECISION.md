## 0. TL;DR（决策摘要）

| 问题 | 结论 |
|---|---|
| **main.rs 用 lib crate 还是内联声明 mod？** | **内联声明**。`main.rs` 自己 `mod data/engine/game/net/ui/utils;`，**完全没有** `use devilutionx_rs::` 或 `crate::`（lib）。lib.rs 和 main.rs 是**两棵独立的、并行的 mod 树**，共享同一份 `src/*.rs` 文件。 |
| **接入 levels 会产生符号冲突吗？** | **不会。** 实测：在 `main.rs` 加一行 `mod levels;` → `cargo check --bin devilutionx` **零编译错误**（2534→2818 个 warning，全是 levels 死代码告警）。 |
| **R2 报告的"必须先解决 mod 结构"对吗？** | **错。** 那是推测，未经实测。接入 levels **几乎零成本**。 |
| **推荐路径** | **路径 A（接入 levels/）**，但分两段：**A1（即时，<1 天）** 把 `mod levels;` 加入 main.rs + 让 `levels/town.rs` 与现有 `TownLayout` 桥接；**A2（中期，多周）** 用真实 DRLG 替换 `DungeonMap`。理由见 §5。 |
| **接入 levels 的最大障碍（Top 3）** | 不是符号冲突，而是：① **两套地牢状态结构并存**（`game_state.rs` 用 `DungeonMap`+`TownLayout`，levels 用 `Dungeon`），接线需选一个作为权威；② **levels DRLG 不读 MPQ**（只产 tile-id/dPiece），渲染素材仍依赖 `engine::dungeon::DungeonLevelData`；③ `Point`/`DungeonType`/`Difficulty` 同名异义（game:: vs levels::），需消歧但不阻塞编译。 |

## 1. 当前 mod 结构事实

### 1.1 lib.rs（库 crate，`src/lib.rs`）

```rust
pub mod controls;
pub mod data;
pub mod engine;
pub mod ffi;
pub mod game;
pub mod levels;   // ← levels 只在这里声明
pub mod net;
pub mod panels;
pub mod ui;
pub mod utils;
```

### 1.2 main.rs（二进制，`src/main.rs` 第 12–17 行）

```rust
mod data;
mod engine;
mod game;
mod net;
mod ui;
mod utils;
```

**关键事实（实测）：**
- main.rs **不依赖 lib crate**。全文 grep：0 处 `devilutionx_rs::`，0 处 `use crate::`（指 lib root）。
- main.rs 用**内联 `mod` 声明**重建了它自己的 mod 树，指向**同一批 `src/*.rs` 文件**（`src/engine/`、`src/game/` 等被两棵树共享）。
- **lib 树 vs 二进制树的差异**：
  - lib.rs 多声明：`controls`、`ffi`、`levels`、`panels`。
  - main.rs 少这四个。
- 因此 `levels/`（以及 `controls/`、`ffi/`、`panels/`）**只在库 crate 编译，不进二进制**。`GameState`、游戏循环跑的全是二进制树（`game/`、`engine/`）。
- **为什么 levels 不在 main.rs？** 不是技术冲突，而是**历史遗漏**：M6（Day46–60）移植 levels/ 时只接到了 lib.rs；后续 M25–M80 的所有游戏系统集成都在 main.rs 树内完成，没人回头补 `mod levels;`。`controls`/`panels` 同理（main.rs 的 UI 是内联手写的，没用这些端口）。

### 1.3 levels/ 目录（13 个文件，~470KB）

```
src/levels/
├── mod.rs            (模块声明 + pub use 重导出)
├── gendung.rs  19KB  (Dungeon 结构：dPiece/dFlags/dMonster/dPlayer/dObject/dLight 全层)
├── types.rs    11KB  (DungeonType/MAXDUNX/DMAXX/DungeonFlag/MegaTile/Micros)
├── town.rs     22KB  (create_town + TownGenerator::fill_sector，固定 Tristram 布局)
├── drlg_l1.rs  51KB  (Cathedral DRLG，56 个函数，miniset 房间算法)
├── drlg_l2.rs 118KB  (Catacombs DRLG，走廊+房间)
├── drlg_l3.rs  62KB  (Caves DRLG)
├── drlg_l4.rs 129KB  (Hell DRLG，河流/房间)
├── trigs.rs    24KB  (楼梯/传送点触发器)
├── themes.rs   15KB  (Theme 房间布置)
├── tile_properties.rs 14KB
├── setmaps.rs  14KB  (任务关卡/竞技场)
└── level_manager.rs 13KB
```

`levels/mod.rs` 用 `pub use ...::*` 重导出（`gendung::*`、`types::*`、`drlg_l1::*` 等），但这些重导出**只在 `levels::` 命名空间内可见**，不会污染 crate root，因此与 `game::` 同名项互不冲突。

## 2. 接入 levels 的编译错误清单（实测）

### 2.1 实验方法
1. 在 `src/main.rs` 第 12–17 行的 mod 块中插入 `mod levels;`（`git diff` 仅 +1 行）。
2. `cargo check --bin devilutionx 2> levels_check.txt`。
3. 统计 error / warning。
4. `git checkout src/main.rs` 恢复（已确认工作树干净）。

### 2.2 结果

| 指标 | 基线（无 levels） | 加 `mod levels;` 后 | 变化 |
|---|---|---|---|
| **编译错误** | **0** | **0** | **+0** |
| 编译结果 | `Finished` | `Finished` | 仍成功 |
| warning 总数 | 2534（122 dup） | 2818（131 dup） | **+284** |
| 退出码 | 0 | 0 | — |

**新增的 284 个 warning 全部是 levels/ 的死代码告警**（"is never used/constructed"），分类（按频率）：

| warning 类型 | 数量 | 含义 |
|---|---|---|
| `multiple associated items are never used` | 132 | levels 的函数/方法未被任何调用者引用 |
| `use of deprecated method rand::Rng::gen_range` | 44 | levels 用了旧 rand API（renamed to `random_range`） |
| `associated function new is never used` | 43 | 构造函数未用 |
| `function miniset_varchNN/miniset_harchNN/... is never used` | ~80 | drlg_l1 的 miniset 工厂函数未用 |
| `struct Point/Rectangle/Size/Displacement is never constructed` | ~33 | levels 内部的几何类型（注：levels 用的是 `crate::engine::Point`，这里的 Point 是别处） |
| `constant TILE_WIDTH/TILE_HEIGHT is never used` | 14 | 常量未用 |

**结论：接入 levels/ 零编译成本，零符号冲突。** 唯一"代价"是 +284 条死代码告警，且其中 44 条是真实的 `rand` API 过时告警（`gen_range`→`random_range`），与接入无关，是 levels/ 自身的代码质量问题。

### 2.3 为什么没有符号冲突？（机制解释）

侦察假设（200 报告 R2）以为 levels 的 `DungeonType`/`Difficulty`/`Point`/`DMAXX` 会和 game/ 撞名。实测不撞，原因：

1. **levels/ 全部用绝对命名空间路径**。例如 `levels/types.rs` 第 6 行 `use crate::engine::Point;`，`levels/town.rs` 第 5 行 `use crate::levels::gendung::Dungeon;`。编译器永远能解析到唯一目标。
2. **`Point` 是共享类型**。levels 用的 `Point` = `crate::engine::Point`（engine/mod.rs:75 重导出）。game/types.rs 里**另有一个** `Point`（第 223 行），但它在 `game::types::Point` 命名空间，与 engine 的并存。levels 不碰 game 的 Point。
3. **同名异义的枚举**（`levels::types::DungeonType` vs `game::types::DungeonType`，`Difficulty` 同理）位于不同 mod，Rust 的名字解析按路径区分，**根本不会触发 E0252/E0428**（重复定义）。
4. **DMAXX/MAXDUNX**（levels/types.rs:26–37）是 `levels::types` 内的常量，game/types.rs 没有 MAXDUNX/DMAXX（它有 NUM_LEVELS/MAX_MONSTERS 等不同名），**无重名**。

> 唯一理论上的风险是有人写 `use levels::types::*; use game::types::*;` 这种 glob 导入到同一作用域——目前无人这么做，且 levels/mod.rs 的 glob 只在 `levels::` 内展开。

## 3. 两条战略路径对比

### 路径 A：接入 levels/（忠实 C++ 路径）

**做法**：`mod levels;` 入 main.rs → 让游戏循环调用 `levels::town::create_town()` / `levels::drlg_l1::...generate()` 产 dPiece → 渲染器读 dPiece + `engine::dungeon::DungeonLevelData`（MIN/TIL/SOL/CEL）出图。

| 维度 | 评估 |
|---|---|
| **mod 接入** | ⭐ 几乎零成本（实测 0 错误）。改 main.rs 1 行 + 可能让 levels/mod.rs 的 pub use 收敛（可选）。 |
| **符号冲突** | 无（见 §2.3）。 |
| **可获得的忠实度** | ⭐⭐⭐⭐⭐ 真 DRLG（Cathedral/Catacombs/Caves/Hell 四套算法已端口）、真 dPiece 层、真 Tristram 固定布局、楼梯触发器、Theme 房间。与 C++ `Source/levels/` 一一对应。 |
| **渲染对接难度** | 中。levels 产 dPiece（tile-id），但 dPiece→像素仍需 `engine::dungeon::DungeonLevelData`（已能读 MPQ 的 MIN/TIL/SOL）+ 一座 "dPiece index → MegaTile → 16 micros → RGBA → SDL Texture" 的桥（200 报告 Step 2 的桥，独立于本决策）。 |
| **状态结构整合** | ⚠️ 中等工作量。`game_state.rs` 现持 `DungeonMap`（简版，50×50 TileType）+ `TownLayout`（自己拼的 d_piece Vec）。levels 的 `Dungeon`（MAXDUNX×MAXDUNY=112×112，全层）更完整但更大。需决定：GameState 持有哪一个？最干净是让 `Dungeon` 成权威，`DungeonMap` 退役；或写适配器把 `Dungeon` 的 dPiece 投影成 `TownLayout`。 |
| **风险** | 低（编译已验证）。主要未知是 levels DRLG 算法正确性（M6 移植，无端到端测试验证产出的 dPiece 能正确出图），但这是"内容正确性"风险，不是"接入"风险。 |
| **预估工作量** | **接入并跑通 town：1–2 天**（含 state 整合）；**接入并跑通 Cathedral（drlg_l1）：3–5 天**；**四层全通：2–3 周**（drlg_l2–l4 体量大，118/62/129KB）。 |

### 路径 B：继续用 game/dungeon.rs（简化路径）

**做法**：不碰 levels，在 `game/dungeon.rs::DungeonMap`（50×50，`TileType` 枚举网格，过程化随机房间+走廊）基础上扩展，自己实现 town 布局和渲染。

| 维度 | 评估 |
|---|---|
| **mod 接入** | 无需（已在 main.rs 树）。 |
| **符号冲突** | 无。 |
| **忠实度** | ⭐ 偏离 C++。`DungeonMap` 是**自创的过程化生成器**，TileType 是 Rust 枚举（Wall/Floor/Door/Corridor），**没有 dPiece 层、没有 MIN/TIL 索引、没有 MegaTile 概念**。要渲染必须自建 "TileType→CEL frame" 映射，等于重造 levels 的下半段。 |
| **town** | ❌ `DungeonMap::generate(Cathedral)` 产的是随机 Cathedral，**没有 town 模式**。当前 `GameState::new(player, true, seed)`（is_town=true）实际上绕开了 DungeonMap，靠 `main.rs::build_town_layout` 从 4 个 sector.dun 手拼 `TownLayout.d_piece`（Vec<u16>）——这恰恰是**重新实现了 `levels/town.rs::TownGenerator::fill_sector` 已经做过的事**，且后者更忠实。 |
| **可玩地牢** | ⚠️ DungeonMap 能产"可走"的随机网格，但**不是 Diablo 的地牢**（布局、房间尺寸、楼梯位置、主题房间全不对）。 |
| **预估工作量** | 让 town 可渲染：已在做（TownLayout 存在）。让"像 Diablo 的地牢"可玩：**数周**，且产出的东西仍不忠实，等于把 levels 的 DRLG 用更差的方式重写一遍。 |

### 对比矩阵

| 维度 | 路径 A（levels） | 路径 B（game/dungeon） |
|---|---|---|
| mod 接入成本 | ⭐ 极低（0 错误） | ⭐ 零 |
| C++ 忠实度 | ⭐⭐⭐⭐⭐ | ⭐ |
| 渲染桥需求 | 相同（都要 dPiece→Texture 桥） | 相同 |
| town 重复劳动 | 无（用 levels/town） | 已重复实现（TownLayout） |
| 地下城 DRLG | 现成 4 套（drlg_l1–l4） | 需自写且不忠实 |
| 长期技术债 | 低（与 C++ 对齐） | 高（维护两套平行系统） |
| 对"移植完成"目标契合度 | ⭐⭐⭐⭐⭐ | ⭐⭐ |

## 4. 推荐：路径 A（接入 levels/）

### 理由

1. **接入门槛被证伪。** 200 报告 R2 说"必须先解决 mod 结构"，实测是错的——加 `mod levels;` 零编译错误。继续走 B 的唯一技术理由（"避免 mod 冲突"）不成立。
2. **levels/ 是已完成的忠实端口，丢弃是纯浪费。** drlg_l1–l4 + gendung + town 合计 ~470KB 移植代码，对应 C++ `Source/levels/` 几乎全部。路径 B 等于把这堆资产闲置，另写一套更差的。
3. **路径 B 已经在重复 levels 的工作。** 当前 `main.rs::build_town_layout` + `TownLayout.d_piece` 就是手写版 `levels/town.rs::TownGenerator::fill_sector`。两套 town 布局代码并存，正是 200 报告 R3 警告的"两套并行地牢系统让人困惑"的实例。
4. **渲染管线与选哪条路无关。** 无论 A/B，"dPiece/TyleType → SDL Texture"这座桥（200 报告 Step 2，R1 最大未知）都要建。既然桥一样，数据源应该选更忠实的（levels）。
5. **"移植完成"的语义要求忠实度。** 项目定位是 "Rust port of DevilutionX"，不是 "Diablo-like game"。路径 B 的随机地牢不是 Diablo 的地牢，达不到移植目标。

### 风险与缓解

- **R-A1：levels DRLG 正确性未验证。** drlg_l1–l4 是 M6 端口，没有端到端测试证明产出的 dPiece 能正确渲染出 C++ 一致的地图。**缓解**：接入后先跑 town（固定布局，最易验证），再逐层 spike drlg_l1，对照 C++ 截图/参考存档。
- **R-A2：GameState 状态整合。** `game_state.rs` 持 `DungeonMap`+`TownLayout`，levels 持 `Dungeon`。需统一。**缓解**：见 §5 步骤 2 的"适配器"方案，渐进迁移，不一次性推翻。
- **R-A3：rand API 过时。** levels 用 `gen_range`（44 处 warning），rand 0.9 已改名 `random_range`。**缓解**：接入后跑一次 `cargo fix` 即可，机械改动。

## 5. 路径 A 分步接入计划

> 原则：**渐进、可回退**。每步保持二进制可编译可运行。

### Step 0：接入 mod（即时，<0.5 天）
- 在 `src/main.rs` mod 块加 `mod levels;`。
- 跑 `cargo check --bin devilutionx` 确认 0 错误（预期 +284 死代码 warning）。
- **验收**：二进制仍正常运行；levels 代码进入编译但尚无调用者。
- **可选清理**：把 `levels/mod.rs` 的 `pub use drlg_l1::*;`（drlg_l1 未做选择性重导出）收敛为显式列表，减少 glob 污染。非必需。

### Step 1：消歧同名类型（<0.5 天，可选但建议）
- 在调用 levels 的文件里，统一用**全路径** `levels::types::DungeonType`、`levels::gendung::Dungeon`，避免与 `game::types::DungeonType` 混淆。
- 不改 levels/ 内部，只在接缝处用显式路径。
- **验收**：无 `ambiguity`/`mismatched types` 错误。

### Step 2：让 town 走 levels（1–2 天）
- **目标**：用 `levels::town::create_town(TownEntry::Main, 0)` 替代当前 `main.rs::build_town_layout` 的手拼逻辑。
- **关键差异**：
  - 当前 `TownLayout.d_piece` 是 `Vec<u16>`（动态），范围 `TOWN_MAX_X×TOWN_MAX_Y`。
  - `levels::town::TownGenerator.d_piece` 是 `[[u16; MAXDUNY]; MAXDUNX]`（112×112 静态）。
  - `create_town()` 目前**只设 bounds + spawn，不调 fill_sector**（fill_sector 需要外部传入 sector 的 mega-tile 数据）。需在调用处补 `fill_sector` 四次（对应 sector1s–4s.dun），或扩展 `create_town` 内部完成。
- **写一个适配器**：`TownGenerator → &TownLayout` 视图，或直接把 `GameState.town_layout` 字段类型换成持有 `levels::gendung::Dungeon`（更彻底）。
- **验收**：进 town 后渲染出的 Tristram 布局与之前一致（dPiece 非零格数同量级），玩家站在 (75,68)。

### Step 3：建 dPiece → 渲染桥（与 200 报告 Step 2 合并，1–2 天）
- 这一步**独立于 A/B 决策**：无论数据来自 levels 还是 TownLayout，都要把 dPiece index → `DungeonLevelData` 的 MegaTile → 16 micros → 调色板 RGBA → SDL Texture。
- 复用 `engine::dungeon::DungeonLevelData`（已能 `load_from_asset_manager` 读 town.min/til/sol）。
- **验收**：屏幕上出现真实 Tristram 地砖（非绿块）。这正是 200 报告的 Step 2/3。

### Step 4：接入 Cathedral（drlg_l1，3–5 天）
- 在"进入地下城"流程里调 `levels::drlg_l1` 的 `generate(DungeonType::Cathedral, seed)` 产 `Dungeon.tiles` + `Dungeon.pieces`（dPiece）。
- 用 Step 3 的桥渲染 l1data 的 MIN/TIL。
- **对照验证**：用固定 seed 对比 C++ 参考截图（或存档的 dPiece 转储）。
- **风险点**：drlg_l1 的 miniset/房间算法若端口有 bug，产出的 dPiece 会错乱。准备回退到 town-only。

### Step 5：四层全通（drlg_l2–l4，2–3 周）
- 逐层接入，每层对照 C++ 验证。
- drlg_l2（118KB）/l4（129KB）体量大，预计每层 4–6 天含调试。

### Step 6：退役 DungeonMap（收尾）
- 确认 levels::Dungeon 完全覆盖后，从 `game_state.rs` 移除 `DungeonMap` 字段及相关生成代码。
- 删除/归档 `game/dungeon.rs`（或保留为单元测试夹具）。
- **验收**：grep 确认无 `DungeonMap` 残留引用。

## 6. 若选路径 B：game/dungeon.rs 需补什么

> 不推荐，但为完整性列出。要让 `DungeonMap` 生成"可玩且像 Diablo 的地牢"，需自建：

1. **dPiece 层**：`DungeonMap` 现在只有 `TileType`（Wall/Floor/...），**没有** dPiece（micro-tile 索引）。渲染需要 dPiece 索引 `DungeonLevelData` 的 MegaTile。需加一个 `tile_id: [[u16; H]; W]` 字段并实现 "TileType → tile_id" 映射（这正是 levels/types.rs + gendung.rs 已有的）。
2. **Town 模式**：`DungeonMap::generate` 无 town 分支。需加固定布局加载（= 重写 `levels/town.rs`）。
3. **忠实 DRLG**：当前 `generate` 是通用 BSP/房间走廊，不是 Cathedral 的 chamber+miniset 算法。要像 Diablo 需重写（= 重写 `drlg_l1.rs` 56 个函数）。
4. **楼梯/触发器**：无。需加（= 重写 `levels/trigs.rs`）。
5. **Theme 房间**：无。需加（= 重写 `levels/themes.rs`）。

**结论**：路径 B 要达到路径 A 的起点，等于把 levels/ 重写一遍，且大概率不如已经端口+对照过 C++ 的 levels/ 忠实。**无性价比。**

## 7. 意外发现

1. **main.rs 与 lib.rs 是两棵独立 mod 树共享同一份源文件**，而非"二进制依赖库 crate"。这意味着改 `src/game/*.rs` 同时影响两棵树；也意味着 lib crate 里的 `levels`/`controls`/`panels`/`ffi` 对二进制完全不可见。**架构债**：长期应让二进制 `use devilutionx_rs::*;` 消除双树，或明确分工（lib=引擎，bin=装配）。但这是独立的大重构，不在本决策范围。
2. **`Point` 类型有三处定义**：`engine::point::Point`、`engine::types::Point`（第 306 行）、`game::types::Point`（第 223 行）。levels 用 `engine::Point`（engine/mod.rs 重导出，指向 `engine::types::Point`）。这是历史遗留的重复，建议统一到 `engine::Point`，但非本任务阻塞项。
3. **`engine::archive::ArchiveManager`（200 报告接线机会 #1）和 `levels/` 一样未进二进制**——它在 `engine/mod.rs` 里（`pub mod archive;`），所以**已经在** main.rs 的 `mod engine;` 树内编译了，只是没被调用。与 levels 不同，levels 是整个 mod 缺声明。
4. **levels/town.rs 的 `create_town` 是半成品**：设了 bounds/spawn 但不自动 fill_sector，需调用者补。接入时要把当前 `main.rs::read_dun_template` + `build_town_layout` 的 sector 加载逻辑搬进 `create_town` 或其包装。
5. **rand 0.9 API 迁移是 levels/ 的现存技术债**（44 处 `gen_range` deprecated），接入后应顺手 `cargo fix`。

### 1. Core Animation System#### update_animation() - Enhanced

**C++ Reference**: `Source/objects.cpp` lines 4268-4278

```rust
pub fn update_animation(&mut self) {
    if !self.anim_flag {
        return;
    }

    self.anim_cnt += 1;

    if self.anim_cnt < self.anim_delay {
        return;
    }

    self.anim_cnt = 0;
    self.anim_frame += 1;

    // Loop animation (frame wraps from len back to 1, not 0)
    if self.anim_frame > self.anim_len {
        self.anim_frame = 1;
    }
}
```

**Key Features**:
- ✅ Respects `anim_flag` (only animates when true)
- ✅ Increments `anim_cnt` each tick
- ✅ Advances frame when `anim_cnt >= anim_delay`
- ✅ **Loops from anim_len → 1** (not 0, matching C++)
- ✅ Resets counter on frame advance

### 3. Object-Specific Animation Handlers

#### update_door_animation()

**C++ Reference**: `Source/objects.cpp` UpdateDoor()

```rust
pub(crate) fn update_door_animation(door: &mut Object) {
    let state = door.get_door_state();

    match state {
        DoorState::Closed => {
            // Door is closed, reset to frame 1
            if door.anim_frame != 1 {
                door.anim_frame = 1;
                door.anim_cnt = 0;
            }
        }
        DoorState::Open => {
            // Door is open, stay at last frame
            if door.anim_frame < door.anim_len {
                door.anim_frame = door.anim_len;
            }
        }
        DoorState::Blocked => {
            // Door is blocked, stop animation
            door.stop_animation();
        }
    }
}
```

**Logic**:
- **Closed**: Force frame to 1 (closed position)
- **Open**: Force frame to last frame (fully open)
- **Blocked**: Stop animating entirely

#### update_sarcophagus_animation()

**C++ Reference**: `Source/objects.cpp` UpdateSarcophagus()

### 4. ObjectManager Batch Processing

#### process_animations()

**C++ Reference**: `Source/objects.cpp` ProcessObjects() lines 4201-4278

```rust
pub fn process_animations(&mut self) {
    for slot in self.objects.iter_mut() {
        if let Some(object) = slot {
            // Update object-specific logic
            match object.otype {
                // Static objects (stop animation)
                ObjectId::Barrel
                | ObjectId::BarrelEx
                | ObjectId::ShrineL
                | ObjectId::ShrineR => {
                    object.stop_animation();
                }

                // Doors (update door state)
                ObjectId::L1LDoor
                | ObjectId::L1RDoor
                | ObjectId::L2LDoor
                | ObjectId::L2RDoor
                | ObjectId::L3LDoor
                | ObjectId::L3RDoor => {
                    update_door_animation(object);
                }

                // Sarcophagus
                ObjectId::Sarc | ObjectId::L5Sarc => {
                    update_sarcophagus_animation(object);
                }

                // Default: just update animation
                _ => {}
            }

            // Update animation frame
            object.update_animation();
        }
    }
}
```

**Features**:
- ✅ Stops animation for static objects (barrels, shrines)
- ✅ Calls door-specific update logic
- ✅ Calls sarcophagus-specific update logic
- ✅ Updates all animated objects' frames

## Lessons Learned

### 1. Field Naming Consistency

**Issue**: Assumed `door_state` field existed, but C++ uses generic `_oVar` fields

**Lesson**: Always verify C++ field names before assuming Rust equivalents

**Prevention**:
- Document all `ovar1-6` usages in C++ comments
- Add field purpose comments (e.g., `pub ovar4: i32, // Door state`)

### 2. Animation Frame Indexing

**Issue**: Confusion between 1-indexed (internal) and 0-indexed (rendering)

**Lesson**: C++ animations use 1-based indexing internally, convert to 0-based for rendering

**Best Practice**:
- Keep internal frames 1-indexed (matching C++)
- Provide `get_animation_frame()` for 0-indexed output
- Document indexing clearly in comments

### 3. Test-Driven Development Success

**Observation**: 23 tests caught 2 critical bugs before integration

**Success Factors**:
- Wrote tests based on C++ behavior first
- Tested edge cases (closed, open, blocked states)
- Integration tests caught cross-function issues

**Recommendation**: Continue test-first approach for all future modules
